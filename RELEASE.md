# Building & releasing `zs-proxy`

The CLI is this repo's Go module, built as the binary `zs-proxy`. Release is
goreleaser-driven; the load-bearing platform detail is macOS **code signing**,
which is what makes the Keychain wallet backend work prompt-free.

Everything below is one `make` command per step. Run from the repo root.

> **Source and releases share one repo, `txnlab/zs-proxy`.** goreleaser
> publishes the signed archives to its Releases (`release.github` in
> `.goreleaser.yaml`, named explicitly so a fork's release can't land
> elsewhere), and the Homebrew cask, Scoop manifest, `install.sh` and the
> update checker all point there. The autogenerated changelog is **disabled**
> in favor of a curated `RELEASE_NOTES.md`; without one the release body is
> empty (see "Cutting a release").

## TL;DR

**One-time setup** (pick the path you need):

```bash
make dev-cert                                   # local dev: self-signed identity (no Apple account)
make notary-setup APPLE_ID=you@x.com TEAM_ID=ID # release: store notarytool creds (after creating a Developer ID cert, below)
```

Releases build with `GOWORK=off`, so they fetch `github.com/TxnLab/zerosignal/go` at its pinned
version from the public module proxy, with no `GOPRIVATE` needed.

**Every release** (on a macOS host):

```bash
make release-check                              # validate .goreleaser.yaml
export MACOS_SIGN_IDENTITY="Developer ID Application: … (TEAMID)"
make release-snapshot                           # full dry-run, no publish
git tag vX.Y.Z && git push origin vX.Y.Z
make release-notes                              # draft RELEASE_NOTES.md with a model (needs a running proxy), then edit it
make release                                     # builds, signs, publishes to txnlab/zs-proxy, then notarizes
```

(`make release` injects `GITHUB_TOKEN` from `gh auth token` and runs `make notarize`
itself. The release goes public immediately; notarization lands a few minutes later
and back-fills via Gatekeeper's online check — the binaries are unstapled — so a
download made in that window self-heals once Apple approves.)

**Local signed dev build** (just to stop your own Keychain prompting):

```bash
MACOS_SIGN_IDENTITY="zerosignal Local Dev" SIGN_NO_TIMESTAMP=1 make signed
```

## Distribution repos

| Repo | Visibility | Holds | Role |
|---|---|---|---|
| `txnlab/zs-proxy` | public | source; signed binaries + `install.sh` in Releases | you run `make release` here; cask/scoop/installer download URLs point here |
| `txnlab/homebrew-tap` | public | `Casks/zs-proxy.rb` | `brew install txnlab/tap/zs-proxy` |
| `txnlab/scoop-bucket` | public | `zs-proxy.json` manifest | `scoop install zs-proxy` (Windows) |

The `zerosignal.ai/install.sh` redirect is served by the zerosignal.ai web app's
deploy, not from here — see [The install script](#the-install-script).

`GITHUB_TOKEN` must have write access to **all three** distribution repos:
`txnlab/zs-proxy` (to create the release), `txnlab/homebrew-tap` (to commit the
cask), and `txnlab/scoop-bucket` (to commit the manifest). A token from
`gh auth token` works if your account has write on those org repos. goreleaser
does **not** read the gh CLI's stored token automatically — export it.

> **Windows install** (Scoop): `scoop bucket add txnlab https://github.com/txnlab/scoop-bucket`
> then `scoop install zs-proxy`. The windows `.zip` archives are also attached to
> the `zs-proxy` release for direct download. (The binaries aren't Authenticode-
> signed yet — that's a follow-up.)

## The install script

The public one-liner is

```bash
curl -fsSL https://zerosignal.ai/install.sh | sh              # zs-proxy
curl -fsSL https://zerosignal.ai/install.sh | sh -s -- zs-node # zs-node
```

and it resolves like this:

```
scripts/install.sh                ← the ONLY copy anywhere (CI-tested here)
        │ goreleaser release.extra_files
        ▼
github.com/txnlab/zs-proxy/releases/latest/download/install.sh
        ▲ 307 redirect, from the zerosignal.ai web app's deploy config
        │
https://zerosignal.ai/install.sh
```

Serving it as a **release asset** rather than from `main` is deliberate: an
edit to `scripts/install.sh` reaches users only when a release carries it, the
same as the binaries it installs. There is one file, so there is nothing to
sync — the only thing pinned elsewhere is the redirect *target*, which is a URL.

Three consequences worth knowing before you cut a release:

- **`latest/download` publishes instantly.** The moment a release goes out, its
  `install.sh` is what every `curl | sh` in the world runs. It's covered by
  `scripts/install_test.go` and `make lint-sh`, but there is no staging step.
- **A script-only fix does not need a release:**
  `gh release upload <tag> scripts/install.sh --repo txnlab/zs-proxy --clobber`.
- **The redirect lives in the zerosignal.ai web app's deploy config** and ships
  on that app's deploy cadence, not this one. It points at `latest`, so it needs
  no attention per release — but if it is ever repointed, that is where.

The script serves **both** products from this one copy; `zs-node` publishes no
installer of its own. It fetches the release archive over TLS and verifies the
sha256 against the release's own `checksums.txt`. Be precise about what that
buys: nothing signs `checksums.txt`, so it defends against corruption,
truncation, and a stale CDN object — **not** against a compromised release.
Release signing (cosign/minisign with a key pinned in the script) is a follow-up
alongside Windows Authenticode. Don't make the verification conditional on a
digest tool being present, which would be worse than none.

## What the pipeline does

`make release` / `release-snapshot` first resolve the newest patch of `go.mod`'s
Go minor from go.dev (`scripts/release-toolchain.sh`), and run goreleaser under
that `GOTOOLCHAIN`. So the binaries build on the latest patch, not on the Go you
have installed; the first run downloads that toolchain. Both targets need the
network, and both stop if go.dev can't be reached or no longer lists the minor
as supported. In that case move `go.mod`'s `go` directive to a supported minor,
and CI's `go-version` with it. CI resolves the newest patch from go.dev the same
way, after `setup-go`, so its jobs stop on the same two conditions.

goreleaser then:

- builds **darwin amd64 + arm64** (CGO=1, must run on a macOS host) and combines
  them into a single **universal** binary; builds **linux + windows** amd64/arm64
  (CGO=0, cross-compiled);
- **code-signs** the universal darwin binary via the `universal_binaries`
  post-hook (`scripts/sign-macos.sh`, hardened runtime + `build/entitlements.plist`)
  using the exported `MACOS_SIGN_IDENTITY`;
- produces archives + `checksums.txt`, **publishes a GitHub Release in the
  public `txnlab/zs-proxy` repo** (`draft: false` — immediate; published
  alongside the manifests so the tap download URLs resolve right away), and writes
  the Homebrew cask (`txnlab/homebrew-tap`) + Scoop manifest (`txnlab/scoop-bucket`);
- attaches `scripts/install.sh` unchanged as a release asset (`release.extra_files`),
  which is what `https://zerosignal.ai/install.sh` resolves to — see
  [The install script](#the-install-script);
- stamps `internal/build` with `Version`, `Commit`, and `KeyringBackend=os`.

That `KeyringBackend=os` stamp is why signing matters: a **code-signed** binary
earns a persistent macOS Keychain trust ACL and never re-prompts, so the wallet
uses the OS Keychain. An **unsigned** binary can't, so it falls back to the
encrypted-file backend (or nags on every Keychain access). See
[Reference → backends](#wallet-backends).

> **macOS + CGO:** the Keychain backend is build-tagged `darwin && cgo`, so
> darwin builds **must** use `CGO_ENABLED=1` and run on a macOS host. linux and
> windows use pure-Go backends and cross-compile with `CGO_ENABLED=0`.
> `.goreleaser.yaml` already encodes this split — don't fight it.

## One-time setup

### Local dev — self-signed (no Apple account)

Enough to make your local Keychain stop prompting; **not** notarizable and other
machines will still warn.

```bash
make dev-cert     # creates the "zerosignal Local Dev" identity (idempotent)
```

`scripts/dev-cert-macos.sh` generates a code-signing cert, imports it into your
login keychain, and pre-authorizes `codesign` to use it. Remove later with
`security delete-identity -c "zerosignal Local Dev"`.

> The local dev identity and the notary profile keep the **`zerosignal`** brand
> name (not `zs-proxy`): they're account/brand-level and meant to be shared
> across the whole product line (a future `zs-node` reuses the same Apple
> Developer cert + notary profile), so they aren't per-binary.

### Release — Developer ID + notarization

Prerequisite: an active **Apple Developer Program** membership and your **Team
ID** (Apple Developer portal → Membership).

1. **Create the Developer ID Application certificate.** Easiest via Xcode:
   **Settings → Accounts → (your Apple ID) → Manage Certificates → `+` →
   Developer ID Application**. This puts the cert + private key in your login
   keychain. Confirm the exact identity string:

   ```bash
   security find-identity -v -p codesigning
   # → "Developer ID Application: Your Name (TEAMID)"
   ```

2. **Store notarytool credentials** as a keychain profile. First create an
   **app-specific password** at appleid.apple.com → Sign-In & Security (your
   normal Apple ID password will not work), then:

   ```bash
   make notary-setup APPLE_ID=you@example.com TEAM_ID=TEAMID
   ```

   This wraps `xcrun notarytool store-credentials zerosignal-notary …` and omits
   `--password` so notarytool prompts for it (keeping it out of shell history).
   Override the profile name with `NOTARY_PROFILE=…` if needed.

## Local signed build (dev loop)

```bash
MACOS_SIGN_IDENTITY="zerosignal Local Dev" SIGN_NO_TIMESTAMP=1 make signed
./out/zs-proxy version
```

`make signed` stamps `KeyringBackend=os` and code-signs with your identity.
`SIGN_NO_TIMESTAMP=1` is **mandatory for self-signed/ad-hoc certs** — they can't
use Apple's secure-timestamp server. Plain `make zs-proxy` skips signing
entirely and uses the encrypted-file backend (no Keychain prompts, no identity
needed).

## Cutting a release

On a macOS host, with the Developer ID setup above done:

1. **Validate config:**

   ```bash
   make release-check
   ```

2. **Dry-run the whole pipeline** (no publish). `MACOS_SIGN_IDENTITY` must be
   **exported** so goreleaser's signing sub-process inherits it. Do **not** set
   `SIGN_NO_TIMESTAMP` here — Developer ID requires Apple's secure timestamp.

   ```bash
   export MACOS_SIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)"
   make release-snapshot
   ```

3. **Tag and push** the release commit:

   ```bash
   git tag vX.Y.Z && git push origin vX.Y.Z
   ```

4. **Write the release notes.** The auto-changelog is disabled in favor of curated
   notes, which otherwise leaves the release body empty — GitHub then shows the
   repo's HEAD commit subject instead. Draft from the commits since the last tag,
   then **edit it** (it's published as-is):

   ```bash
   zs-proxy proxy start      # the drafting call needs a RUNNING, funded proxy
   make release-notes        # writes RELEASE_NOTES.md from <prev-tag>..HEAD
   $EDITOR RELEASE_NOTES.md  # curate — this becomes the public release body
   ```

   `make release-notes` sends each commit's **full message** since the last tag to a
   model on your running proxy and asks for user-facing notes: a curated summary
   (`Breaking changes` / `Highlights` / `Improvements` / `Fixes` / `Upgrade notes`),
   then a `### Details` narrative. Everything **above** `### Details` is what the
   Discord embed shows, so keep that part tight. There's no version heading — the
   release title and the Discord message already carry it.

   It's a real, billed chat completion against your own wallet, so it needs a funded
   wallet and an operator serving the model. Commit hashes, author names, and file
   paths are never sent; the result is scanned for internals (hashes, paths, names),
   and any hit is printed as a `WARNING`. **It's still a model — read the file before
   you publish it.**

   ```bash
   make release-notes RELEASE_NOTES_MODEL=claude-opus-5   # draft with another model
   make release-notes ARGS=-dry-run                       # print the prompt, no spend
   make release-notes ARGS=-offline                       # plain commit subjects, no model
   make release-notes ARGS="-from v0.9.0"                 # override the range
   ```

   A failed call exits non-zero and leaves any existing `RELEASE_NOTES.md` untouched
   — use `ARGS=-offline` (or `ARGS=-keep-going`) if no proxy is reachable.
   `make release` then sets the body from `RELEASE_NOTES.md` via `gh release edit`
   (goreleaser ignores `--release-notes` when the changelog is disabled). It's
   gitignored + ephemeral, so write it fresh each release; skip it and the body is
   just empty (the prior behavior).

5. **Release for real.** Builds, signs the darwin universal binary, **publishes**
   the release to `txnlab/zs-proxy` + the Homebrew cask / Scoop manifest, then
   **notarizes** (`make release` runs `make notarize` for you). `GITHUB_TOKEN`
   is injected from `gh auth token`; your account needs write on `txnlab/zs-proxy`,
   `txnlab/homebrew-tap`, and `txnlab/scoop-bucket`.

   ```bash
   make release
   ```

   On notarization: `notarytool` **won't accept a `.tar.gz`** (only
   `.zip`/`.pkg`/`.dmg`), so `notarize-macos.sh` extracts the signed binary and
   submits it as a `.zip`. That still notarizes the **binary's code signature
   (cdhash)**, which is the same binary inside the distributed `.tar.gz` — so
   Homebrew installs verify fine. A loose `.tar.gz`/`.zip` **can't be stapled**,
   so Gatekeeper checks notarization **online** on first run. To staple offline,
   wrap the binary in a `.dmg`/`.pkg` (a follow-up). To re-notarize without
   re-releasing, `make notarize` still works standalone.

6. **Verify.** The release is already public (`draft: false`, marked latest) and
   `make notarize` has run — there's no manual publish step. Confirm the release
   page shows your `RELEASE_NOTES.md` body + the expected assets, and that
   `notarytool` reported `Accepted`. Because the binaries are unstapled, Gatekeeper
   checks notarization **online** — a copy downloaded in the brief window before
   Apple approved self-heals on a later run, so no re-publish is needed. (Re-notarize
   anytime with `make notarize` if it failed.)

   Also confirm the installer this release just published actually serves:

   ```bash
   curl -fsSLI https://zerosignal.ai/install.sh | tail -1   # 200 after the redirect
   curl -fsSL  https://zerosignal.ai/install.sh | head -3   # the script, not HTML
   ```

   This matters more than the other assets: `latest/download` means the script
   in *this* release is live for everyone the instant it publishes.

## Discord release announcement

`make release` announces the release to the shared ZeroSignal **#releases**
Discord channel via goreleaser's built-in Discord announcer (`announce.discord`
in `.goreleaser.yaml`). It fires at the very end of `goreleaser release` (real
releases only — `release-snapshot` never announces) and embeds the curated
`RELEASE_NOTES.md` **summary**, so the same notes you publish to GitHub show up in
Discord (goreleaser's own changelog is disabled, so `make release` hands the notes
in via `ZS_RELEASE_NOTES`). The embed gets everything **above** the `### Details`
heading, capped at 3800 bytes — the narrative below it is GitHub-only, and the cut
lands on a section boundary rather than mid-paragraph. `make release-notes` warns
if the summary is long enough to be truncated anyway.

It's **opt-in via the webhook creds** — `DISCORD_WEBHOOK_ID` and
`DISCORD_WEBHOOK_TOKEN`, the two halves of the channel webhook URL
`https://discord.com/api/webhooks/<ID>/<TOKEN>` (Discord: Channel → Integrations
→ Webhooks → New Webhook). With **both** present in the release shell's env,
`make release` flips `ZS_ANNOUNCE_SKIP=false` and the announce runs; leave either
unset and it's silently skipped — the skip is deliberately fail-open so a
creds-less release can't break at the announce step *after* the artifacts are
already public.

Rather than exporting them machine-wide in your shell profile, `make release`
**auto-sources a gitignored `.env.release`** in the repo root if present, so the
creds stay scoped to this repo and this command (`set -a` means the file can use
plain `KEY=value` lines, no `export` needed):

```bash
# .env.release  — gitignored, never committed
DISCORD_WEBHOOK_ID=<ID>
DISCORD_WEBHOOK_TOKEN=<TOKEN>
```

To keep **no plaintext on disk**, stash them in the macOS Keychain (the same
store zs-proxy's wallet uses) once, then have `.env.release` read them back:

```bash
security add-generic-password -U -a "$USER" -s zs-discord-webhook-id    -w '<ID>'
security add-generic-password -U -a "$USER" -s zs-discord-webhook-token -w '<TOKEN>'
```

```bash
# .env.release  (Keychain-backed — nothing secret in the file itself)
DISCORD_WEBHOOK_ID="$(security find-generic-password -a "$USER" -s zs-discord-webhook-id -w)"
DISCORD_WEBHOOK_TOKEN="$(security find-generic-password -a "$USER" -s zs-discord-webhook-token -w)"
```

**Avatars — two spots, both the ZeroSignal mark (`logo.png`).**
- **Webhook avatar** (big, next to the bot name) — upload `logo.png` in Discord
  (Server Settings → Integrations → Webhooks → pick the webhook → upload image +
  name). goreleaser posts *through* the webhook and can't set this.
- **Embed author icon** (small, next to `zs-proxy releases` inside the embed) —
  goreleaser's `icon_url`, pointed at `logo.png` at the root of this repo's
  `main`. **Keep that file there**, or goreleaser falls back to its **own gopher
  mascot** — a blank `icon_url` is defaulted to
  `goreleaser.com/static/avatar.png`, not to "no icon". (goreleaser likewise forces
  the author *text*: blank prints "GoReleaser", so it stays "zs-proxy releases".)

`logo.png` is the ZeroSignal SVG favicon rasterized to 512×512
(`rsvg-convert -w 512 -h 512 favicon.svg -o logo.png`) — Discord needs a raster
PNG, not the SVG/ICO favicon.

`zs-node` posts to the **same** channel/webhook; the embed's author line
(`zs-proxy releases` / `zs-node releases`) tells them apart. There's no standalone
announce subcommand in OSS goreleaser, so the first live check is your next real
`make release`.

## CI keychain (optional)

If you sign on a CI runner instead of a laptop, export the cert+key once as a
`.p12`, store it as a CI secret, and at job start:

```bash
security create-keychain -p "$KC_PW" build.keychain
security default-keychain -s build.keychain
security unlock-keychain -p "$KC_PW" build.keychain
security import cert.p12 -k build.keychain -P "$P12_PW" -T /usr/bin/codesign
security set-key-partition-list -S apple-tool:,apple: -s -k "$KC_PW" build.keychain
```

The last line (`set-key-partition-list`) is the non-obvious bit that stops
`codesign` prompting in a headless run.

### Wallet backends

The wallet secret is stored via `99designs/keyring` (through the SDK's `go/wallet`). A new
wallet goes on the backend the `build.KeyringBackend` stamp names (`internal/wallet`), and
`wallet.json` records the backend it landed on, so later runs, and other zerosignal programs
built with another stamp, open it there. `ZEROSIGNAL_KEYRING_BACKEND` overrides both. Under
it, `wallet import --force` of the wallet's own phrase moves the wallet to that backend, while
`wallet new --force` replaces it with a new one.

| Build | `build.KeyringBackend` | Backend | Prompts? |
|---|---|---|---|
| `make zs-proxy` (dev) | `""` | encrypted **file** (JWE: PBKDF2 + AES-256-GCM) | no (passphrase via `ZEROSIGNAL_KEYSTORE_PASSPHRASE` or prompt) |
| `make signed` / goreleaser release | `os` | **OS keychain** (macOS Keychain / wincred / Secret Service) | no — *if code-signed* |

An unsigned macOS binary can't earn a persistent Keychain trust ACL, so it gets
a fresh auth prompt on every access (`-128` if cancelled); a code-signed binary
with a stable identity is trusted after one approval. Hence: dev → file (no
nags); signed release → Keychain.

> The wallet's Keychain service name and the `ZEROSIGNAL_*` env vars keep the
> **`zerosignal`** brand on purpose — renaming the Keychain service would orphan
> any already-stored wallet. The binary is `zs-proxy`; the brand is `zerosignal`.

### Files

- `.goreleaser.yaml` — build matrix (darwin CGO=1, cross CGO=0), universal +
  sign hook, archives, `release.github` → public `zs-proxy` (+ `install.sh` as an
  extra file), Homebrew cask, Scoop bucket.
- `Makefile` — the targets above.
- `scripts/install.sh` — the public `curl | sh` installer, for `zs-proxy` and
  `zs-node` both; tested by `scripts/install_test.go`.
- `scripts/sign-macos.sh` — codesign a binary (`--options runtime`); no-op
  without `MACOS_SIGN_IDENTITY`.
- `scripts/dev-cert-macos.sh` — create a self-signed local dev identity.
- `scripts/notarize-macos.sh` — notarytool submit + staple.
- `build/entitlements.plist` — minimal hardened-runtime entitlements.

**Windows Authenticode** (so the Scoop/direct-download binaries are signed) and
the **winget** manifest are follow-ups.
