# AGENTS.md (proxy)

Technical reference for human developers lives in [`DEVELOPMENT.md`](./DEVELOPMENT.md); [`README.md`](./README.md) is the user-facing front page. Wire spec: [`SPEC.md`](https://github.com/TxnLab/zerosignal/blob/main/SPEC.md). System map: [`README.md`](https://github.com/TxnLab/zerosignal/blob/main/README.md). Both are in [TxnLab/zerosignal](https://github.com/TxnLab/zerosignal), the protocol and SDK repo, which development checks out beside this one as `../proto`; every `proto/…` or `../proto/…` path below is in it. This file is just agent-facing conventions and pitfalls.

**The proxy is a localhost single-user (payer) process, not a multi-tenant server** — the CLI/daemon twin of the zerosignal.ai browser app (`client/`), serving the one payer whose keystore signs `escrow.open`, from that payer's own machine. That framing decides several rules, here and in [`AGENTS.md`](https://github.com/TxnLab/zerosignal/blob/main/AGENTS.md) in TxnLab/zerosignal: why error bodies may be logged, and why the RTT vantage is the payer's own.

## Source of truth

**When sources disagree: tests > code > [`SPEC.md`](https://github.com/TxnLab/zerosignal/blob/main/SPEC.md) > `AGENTS.md` > inline comments.** A disagreement is a **defect to report**, not a gap to guess across — say which two conflict and which you followed. A stale comment is indistinguishable from a live one, so a silent guess becomes the next change's false authority.

**Comments say WHY, never WHAT.** A comment restating the code below it can only ever become false — the code already says it. Explain the constraint, the provider quirk, the rejected alternative, the failure a guard prevents. A load-bearing invariant belongs in a **test**, where it fails loudly, not in prose where it rots quietly. Routing, retry and settlement invariants live in the SDK, where both SDKs replay the golden vectors. Pin them in `../proto`, not here.

**Substantive changes get an independent review before they're reported done.** Spawn a fresh general-purpose subagent, tell it to run the `review` skill, and **name this directory explicitly** — the workspace root is not a git repo, so the skill's opening `git diff` finds nothing there. Hand it the diff and this file, never the reasoning that produced the change. Reviewers are read-only, so a multi-repo change can fan them out in parallel, one per repo. Act on the findings before reporting done.

**Then, and only then, consider `mutation-adversary` — and ask the user first.** It is warranted when the review returned a **Critical**, or when the diff touches a class where a green suite is not evidence: money / settlement / pricing, envelope crypto / AAD / canonical bytes, a security or provenance gate, an added guard or boundary comparison, a retry budget or state machine, or logic mirrored across Go↔TS. Say what it would target and **wait for a yes**; never spawn it on your own judgment. Hand it *only the diff* — the author already tested the failure modes they imagined, so a checker that inherits that reasoning re-tests the same ones. Green tests are not evidence the tests test anything; a surviving mutation is. A clean review is not a reason to skip the ask: review asks *is this code wrong*, mutation asks *would the tests notice if it became wrong*, and a review has come back "sound, no defects" over a diff whose tests then survived two mutations. Most of that class now lives in `../proto`; the proxy's own share is the spend guard, the wallet shim and the CLI's chain writes (`tickets recover`, `slots`, `withdraw`, `close-deposit`, `fund`).

## The payer core is the SDK

Request handling, the body mutators, routing, reserve retry, relay attribution, the 429 rules, receipts, settlement and reconciliation are all `github.com/TxnLab/zerosignal/go/zs` (source `../proto/go/zs`), and their rules are in [`AGENTS.md`](https://github.com/TxnLab/zerosignal/blob/main/AGENTS.md) there. Read that file before changing any of it. A fix goes in `proto/` — commit there, release, then bump this module's require (`go get github.com/TxnLab/zerosignal/go@vX.Y.Z`) in the proxy commit that depends on it. In the workspace `go.work` hides the pin, so a proxy build that passes locally can still fail in CI. Never work around SDK behavior in `internal/`: `client/` runs the TS twin of the same SDK, so a proxy-only patch makes the two payers route differently.

What stays here is the host: the config → `zs.Config` mapping, the spend guard, the ticket journal file, the wallet shim, the CLI, daemon and OS services, and the installer.

- **`server.write_timeout` defaults to `0` and must stay there** (`internal/config/config.go`, pinned in `config_test.go`). The SDK handler takes its `WriteTimeout` from the host, and a non-zero value cuts every stream longer than it mid-generation, after the escrow is already paid. Per-request cancellation comes from the request context.
- **Never log content; the error-envelope carve-out is the SDK's.** The SDK logs *error envelopes* (the operator's and its own) at WARN and nothing else from a body (`../proto/AGENTS.md` "Privacy and logging"). It may do that because the proxy is a localhost single-user process: hiding "your request was rejected because X" from the payer who runs it costs them and protects no one. The node's non-retention guarantee is unaffected. Full request/response dumps are behind `-debug-bodies`, which the CLI maps onto the SDK's debug switch. Don't add any other body logging here.

## Spend and settlement

- **Spend-guard accounting is keyed by ticket id and is exactly-once** (`internal/spend`). `Reserve` / `Settle` / `Release` all take the ticket id, and Settle/Release resolve the amount from the recorded reservation. Three invariants are load-bearing:
  1. **A day roll keeps yesterday's open reservations** (the calendar day, so an idle stretch drops older ones). Any call can roll the day (`Admit`, `Reserve`, `Release`, `Settle`). A ticket reserved before midnight UTC keeps counting against the new day's cap and keeps its id, and its charge lands on the new day's tally when it settles. Dropping them silently loses every in-flight charge at midnight; documented in `spend.go`, pinned by `spend_test.go`.
  2. **A duplicate ticket id is refused, not accepted.** Likewise; `spend.go` has the why.
  3. **A `Release` followed by a late `Settle` records nothing**, which is only safe because the frame factory enforces **one `zs-receipt` frame per stream** (`receiptSeen`). Two frames would otherwise let an operator pick both branches — bad-sig receipt → Release, then a valid one whose Settle finds nothing open — hiding every charge from `spend.daily_cap_usdc`, the payer's only defense against that operator. (This one spans `internal/spend` *and* the SDK's frame factory, `buildFrameFactory` in `../proto/go/zs/dispatch.go`, which is why it stays here.)

  There is **no** deferred-release backstop in the dispatch path: a request whose escrow committed but which never produced a verified receipt keeps its ceiling, because `settleLapsed` can still claim up to `MaxPrice`. The SDK resolves some of these once the chain fixes the outcome. The refund watchdog and the reconciler `Release` on a refund algod accepted. The reconciler also `Settle`s a lapse it sends, at the operator's claim, and `Release`s a closed or lapsed ticket whose journaled receipt the request already settled. That last one frees a reservation a crash inside `Settle` left behind; settling it again would count the charge twice. A lapse the node sends itself, the usual kind, is resolved by neither. Anything none of them sees end holds its ceiling through the rest of its UTC day and the next calendar day. Open reservations are written to `spend-<key>.open.json`, where `<key>` is the SDK's deployment key (`algorand-mainnet-<app id>`), so a restart keeps holding them rather than failing the cap open. Only the guard holding `spend-<key>.json.lock` reads or writes that file; a second proxy on the network keeps its reservations in memory, since writing its own set would erase the holder's. Every proxy on the network in one home (`ZEROSIGNAL_HOME`, below) shares the spent ledger (`spend-<key>.json`); one wallet imported into two homes keeps two tallies, so each home's cap applies separately. A proxy adds to the ledger only under `spend-<key>.json.wlock`, held for one read-and-write: without it, one proxy's write replaces a charge another just recorded. Reserve and Release never write the ledger. A tally with no file yet adopts `spend-<app id>.json` and its open file, the names before 0.7.0 (`spend.Adopt`), but only once no proxy holds that name's lock: an older proxy still serving there would keep writing a file nothing reads, so until it stops this one shares the earlier ledger. `status` reads through `readSpendGuard` and never moves them.
- **Open tickets are journaled to `StateDir/ticket-journal-<deployment key>.json`** (`openTicketJournal` in `internal/app/app.go`), so the SDK's reconciler can settle or refund a ticket left open by a stop or crash. One file per deployment, because the state dir is shared across networks and each process rewrites the whole file. The key comes from `zs.ResolveNetwork` over the same `zs.Network` the client gets (`NetworkFor`, which the spend tally's name uses too), so Run and the SDK name one deployment. The pre-0.7.0 `ticket-journal-<app id>.json` is merged in and removed on open, and the catalog's old name is handed to the SDK to adopt. The SDK locks the file, so a second proxy on the same network gets an in-memory journal with a warning; Run closes the journal after the client, releasing the lock. An unreadable file also falls back to memory and is left in place, never overwritten. The default discovery catalog (`resolveCatalogPath`) is per deployment for the same reason: operator and node ids repeat across networks, so a shared file would seed one network's boot with another's URLs and keys.
- **`zs-proxy tickets` and `close-deposit` read the contract's rules from `escrow.Classify`** (on Solana `zsescrow.Classify`, over the same `settle.Classify`; `../proto/AGENTS.md` "Settlement"). Never re-derive a status/deadline table here. **FROZEN waits for the protocol admin:** its USDC and MBR slot stay locked until the admin's `resolveFrozen` splits the escrow between operator and payer, so `close-deposit` cannot succeed for that payer until then (on a contract without `resolveFrozen`, such as an old localnet deploy, for good). No call the payer can make clears it, and no copy may imply it clears with time. **`Unknown` is never rendered as "too early".**

## Wallet and keystore

- **The keystore must contain the resolved payer address**; the proxy refuses to start otherwise. That's intentional — don't bypass the check. Keys load through the SDK's `wallet.LoadKeys` / `LoadSolanaKeys` (`internal/cli/cli.go`), and `internal/app/app.go::resolveProxyPayerAddr` checks `zs.proxy_payer_addr` with `wallet.ChoosePayer` / `ChooseSolanaPayer`, as `tui -direct` does, so the two payers choose alike. The value is optional: the lone listed key fills it in. With several keys it is required; with none, startup says where keys come from. A set value passes when the keystore can sign for it, which includes a legacy-spacing twin that `Addresses` doesn't list. `zs.New` checks the signer again.

## CLI, daemon, and OS services

- **`app.Run` is a shim over `zs.New`.** The SDK builds the registry, reserve client and wallet from the keystore and network, starts discovery and the protocol-fee read, and `client.Close()` stops discovery. `clientConfigFor` is the whole config→SDK mapping, and the `Run` tests stub the client builder (`Options.buildClient`) so they never see its output, so `client_config_test.go` is all that notices a dropped field — map a new `zs:` knob there and in the test together. The proxy sets `UseEnvProxy`, so `HTTPS_PROXY`/`HTTP_PROXY` still carry node traffic as they did before the SDK, and `warnEnvProxy` says so at startup: the private-address guard sees only the proxy's address.
- **`zs-proxy slots` is the only thing in this module that writes the config file, and it writes it as a line splice.** `internal/config.SetScalar` parses the YAML into a `yaml.Node` **only to locate** the target's line/column, then rewrites that one line — it never re-encodes. A `yaml.Marshal` round-trip is far shorter and is the wrong tool here twice over: it drops the blank lines and comments a user's `config.yaml` inherits from the ~14KB-of-prose `config.example.yaml`, and because `defaults()` seeds the struct *before* unmarshal it would materialize every current default into the file, freezing values we still own. Same reason a missing file is created holding **only** the key being set, never seeded from the example. There is deliberately no `.bak` (a one-line splice has nothing to lose) and deliberately no reuse of `internal/connect.atomicWriteWithBackup` (unexported, 9 call sites, and `config` importing `connect` inverts the layering). The splice refuses rather than guesses on a flow-style mapping or a block scalar — both would reshape the document, not edit a line.
- **Setting the slot count is two operations and both are load-bearing.** The contract admits an open on `(openTickets+1) × mbrForTicket() <= algoBalance`, so the pool's ALGO *is* the concurrency cap and `zs.concurrent_slots` is only the funding target the next top-up aims at. Writing the config without resizing changes nothing; resizing without writing gets re-aimed. Chain goes first, so an unaffordable deposit can't leave a written number the pool doesn't back; a partial one (the wallet funds only the slots it affords) does write it, since it is only the target, and the warning line names the gap. Two asymmetries worth keeping: a shrink's withdraw must be bounded by `zs.FreePoolHeadroom` (the contract reverts on an over-ask, and in-flight tickets hold the rest — say so rather than silently reclaiming less), and the restart warning fires **only on a lowering**, because a running daemon holds the old target in `Wallet.depositSlots` and its next `ensureDepositForServe` would re-deposit what was just reclaimed. A raise has no such failure mode, so warning on it would train the user to ignore the warning. On Solana the pool is the ticket rent pool and the same rules hold: the sizing is `SolanaRentPoolStatus.Shortfall` / `Excess`, a shrink's withdraw is bounded by `Available()`, and both rails reach the action, plan and consent through one `slotsDecisionFor`, so they can't decide differently from the same figures.
- **Graceful stop is cross-platform, but the mechanism differs by OS.** Unix `proxy stop` sends SIGTERM; Windows has no SIGTERM, so it POSTs to a **loopback-only, token-guarded `POST /shutdown`** (`internal/app/shutdown.go`, in front of the SDK handler; the token is generated per-launch, recorded in `daemon.json`, and forwarded to the detached child via `ZEROSIGNAL_SHUTDOWN_TOKEN`). Both cancel the **same `runCtx`** in `app.Run` → one `srv.Shutdown` drain. The route is registered **only when a token is set**, so foreground and service runs don't expose it, and the **token — not the loopback check — is the real guard**: a local web page can reach `127.0.0.1` with a loopback `RemoteAddr`, so without the token it could trigger shutdown. Don't drop the token or widen the route.
- **`ZEROSIGNAL_HOME` is a second home, and the OS service is not its.** `paths.StateDir` and `LogDir` follow `wallet.HomeDir`, so the variable moves every state file, the wallet (its own keychain item) and the logs; the install marker stays in the default dir, since it records the binary. The OS service runs the default home's proxy, so in another home (`paths.OtherHome`, which a variable naming the default dir is not) the lifecycle resolver sees no service (`serviceInstalledHere`), `install-service` / `uninstall-service` refuse before touching the OS manager, and `connect` refuses to write the tools' own configs, which are the user's rather than the home's, without `--print` or `--config-path`. `TestOtherHome_CommandsLeaveTheServiceAlone` and `TestConnect_OtherHomeWritesNoToolConfig` pin the wiring.
- **Lifecycle commands resolve one process owner** (`internal/cli/lifecycle_target.go`): a live self-managed daemon takes precedence when it coexists with an installed OS service (the normal encrypted-file-wallet install state); otherwise `proxy start/stop/restart/status/logs` target the installed service via the OS manager, or the daemon path when no service exists. The both-present choice is printed, not silent. Two load-bearing invariants:
  1. The `f.foreground` guard in `cli.go::run` (`routeStartToService`) must stay. The service itself runs `proxy start --foreground`, so a foreground invocation must serve directly and **never** route back to the service (infinite recursion, or a no-op). The legacy root form calls `f.serve` directly and is exempt.
  2. An installed service bakes its `--config` / `--network` / `--port` in at install time, so start/restart **can't** honor those flags — `warnIgnoredServiceFlags` surfaces that instead of silently reporting success. Changing them means re-running `install-service`.

  `install-service` stops a running self-managed daemon first so the new service can bind the port — but **only when the install auto-enables the service**, i.e. `!wallet.UsesFileBackend()` (`runInstallService` in `service_cmd.go`). A file-backend install isn't enabled at install time (it needs `ZEROSIGNAL_KEYSTORE_PASSPHRASE` wired in first), so it deliberately leaves the daemon serving. That condition is the *source* of the both-present state the precedence rule above resolves, and it is why the resolver exists rather than an assumption that the two are mutually exclusive: `build.KeyringBackend` defaults to `""`, so the file backend — and therefore a live daemon underneath an installed-but-idle service — is the default for any `go build` / `go run` creating a wallet (an existing wallet opens on the backend `wallet.json` records, and `UsesFileBackend` ignores the installing shell's `ZEROSIGNAL_KEYRING_BACKEND`, which the service never sees). Parsing note: `parseDarwinStatus` reads the **first** `state =` / `pid =` from `launchctl print`, because nested sub-dicts emit their own later `state = active` lines that would clobber the job's real state.
- **Windows SCM service specifics** (`internal/cli/service`): it runs as the **installing user** (`ServiceStartName` + a password prompted at install) so it can read that user's Credential Manager wallet and per-user state dir — a LocalSystem service would see neither. It logs to **`proxy.log`** (via `app.Options.LogWriter`) because an SCM process's stderr is discarded. Service mode runs `serveWithContext(allowBootstrap=false)`: it **requires** an existing wallet rather than silently creating an unfunded one with no TTY. The Windows paths are build-tagged (`service_windows.go` / `service_run_windows.go` / `cli/elevate_windows.go`) — keep the `x/sys/windows/svc` deps out of the darwin/linux builds, and keep the `_other.go` stubs in lockstep.
  - **Logon-right grant + UAC self-elevation.** `scmInstall` auto-grants the run-as account `SeServiceLogonRight` via the LSA policy API (`grantServiceLogonRight`, hand-rolled through `advapi32` — `x/sys/windows` doesn't wrap it), so the SCM can start the service without the user touching `secpol.msc`. It must run in **both** the autostart and `!autostart` (file-backend) paths; the latter is the trap, where the service is installed-but-not-started and the user otherwise meets a bare `Error 1069: logon failure` on first manual start. `logonRightError` tailors the message by cause.
  - Installing needs admin (CreateService + the LSA grant), so `cli/elevate_windows.go::ensureElevatedForInstall` raises a UAC prompt and relaunches when not elevated, **pinning the resolved account** onto the relaunch via `--service-account` so over-the-shoulder elevation still installs it to run as the original user (plus a hidden `--uac-relaunch` marker, since the elevated child runs in a fresh console and must print the outcome before it closes). Don't reintroduce a non-zero default password channel via argv or env — the password stays interactively prompted in the (possibly elevated) child.
- **The update checker queries `txnlab/zs-proxy`'s latest GitHub Release only** (`internal/update`), where goreleaser publishes the signed binaries. It compares the latest `vX.Y.Z` tag against `build.Version`, caches the answer on disk with a 24h TTL so at most one command per day touches the network, and tailors the upgrade hint to how the binary was installed (Homebrew / Scoop / `scripts/install.sh` / direct download).

- **`scripts/install.sh` is the public `curl | sh` installer, and the only copy of it that exists.** It serves both `zs-proxy` and `zs-node`, rides out as a release asset (`release.extra_files`), so users get the released copy rather than whatever is on `main`, and `https://zerosignal.ai/install.sh` (a redirect in the zerosignal.ai web app's deploy config) points at `releases/latest/download/install.sh`. It is `#!/bin/sh`, unlike the bash scripts beside it, because it has to run on a stock Alpine/Debian container; everything is in a function with `main "$@"` last so a truncated download can't execute half an installer. Four couplings will break silently if you touch one side only:
  - **The archive `name_template` and the flat archive layout in `.goreleaser.yaml` are a public contract now** — an install.sh already sitting in someone's shell history constructs asset names from them at run time.
  - **The install directory is sticky** (it re-uses the path recorded in the marker). `install-service` bakes the literal `os.Executable()` path into the launchd/systemd unit, so an upgrade that lands the binary elsewhere leaves the service running a binary nothing updates. Don't "simplify" the resolution ladder into a fixed directory.
  - **The marker is what makes `sourceScript` detectable**, and it wins over `classifyPath` — a recorded path is real evidence where a substring guess is not (`classifyPath` cannot distinguish a Scoop install from a Linux user whose `$HOME` is `/home/scoop`). It lives under the **state** dir, not the cache dir, so clearing a cache can't relabel the channel.
  - **The brew/scoop substrings in the script's guard and in `classifyPath` must agree.** `scripts/install_test.go` pins that, along with the darwin-is-universal rule and "a bad checksum installs nothing" — it runs the real script against a fake release under every shell on the box.

## The TEE release lists come from the protocol module

`config.defaults()` seeds `zs.tee.trusted_compose_skeletons` / `trusted_node_images` from
`attest.TrustedComposeSkeletons()` / `attest.TrustedNodeImages()` (`proto/go/attest/releases.go`),
the same lists an SDK caller gets from `tee.DefaultVerifier` (`zs/tee`). zs-node's release CI appends to
them there, so a new node release reaches the proxy through a protocol release and a pin bump —
don't reintroduce a local copy, which would be one more list to fall out of step.

The values are TEE trust anchors: a wrong or missing one makes payers refuse a node silently,
with nothing logged operator-side. They are compiled in deliberately — a served list would
reintroduce the trust root confidential mode exists to remove (SPEC §3e).

### `zs-proxy tee inspect`

`internal/cli/tee.go` replays a node's event log, gates its published app-compose on the measurement, and prints the two release-allowlist values. It calls `attest.VerifyEventLog` / `VerifyAppCompose` / `ExtractComposeSkeleton` rather than re-deriving them — a second copy would agree with the verifier by construction and become a third thing to keep in step with Go and TS. Four rules are load-bearing:

- **Exit 0 for any FINDING** (usage / config / fetch failures still exit non-zero), so a diagnostic never gets wrapped in `|| true`.
- **Each refusal withholds the allowlist values rather than annotating them**: `--file` skips the hash gate and says so, a failed compose gate stops the report, and a `--chain` FAIL stops it too — the replay reads RTMR3 out of the quote and authenticates nothing, so a forged quote would otherwise name its own skeleton digest. `verified` is false on every run without `--chain`.
- **The published-models section prints before the Stop check, on purpose.** An operator chasing a model-binding refusal needs the list even when an earlier gate stopped the report. It carries no trust values, and on a stopped report it omits what a payer would do with the upper half, because a payer never gets that far.
- **The chain line has FOUR states, not two.** A pass on our own STALE cached collateral and a pass on collateral THE NODE SUPPLIED (SPEC §3e's last resort) are both real passes, so the report continues — but each line must name its source, because "verified against Intel's PCK chain, with revocation and TCB collateral" is false about week-old cache and about documents the attested party chose. A refusal reached on our own cached collateral is the fourth, and it STOPS the report: continuing would print a rejected quote's own trust values.
